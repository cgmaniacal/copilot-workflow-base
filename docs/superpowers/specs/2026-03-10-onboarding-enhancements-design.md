# Onboarding Enhancements Design Spec

**Date:** 2026-03-10
**Status:** Draft

## Problem Statement

The current onboarding script makes assumptions that don't hold across all projects:
1. Hardcoded branching strategy (`main/develop/feature/*` with PRs to main) doesn't match teams using multi-environment flows (e.g., `feature/* > develop > pre-release > release`)
2. No CI/CD interaction guardrails — agents have no branch-level access controls
3. Superpowers plugin (4-phase workflow) isn't integrated into the overlay
4. Copilot instructions are a single slim file — insufficient for multi-model coverage (Claude + ChatGPT)
5. No `AGENTS.md` adapter for OpenAI Codex CLI
6. No onboarding documentation for developers who didn't run the setup

## Design

### 1. Configurable Branching Strategy

#### During onboard.mjs

Add interactive prompts after stack detection:

```
Branching Strategy
──────────────────
What branches does your project use? (comma-separated)
> develop, pre-release, release

For each branch, what environment does it map to? (or "none")
  develop → dev
  pre-release → test
  release → uat, prod

Which branches can AI agents push to / create PRs for?
> feature/*, develop

Which branches are protected (agents must NEVER push to)?
> pre-release, release
```

Store as a config object:

```js
const branchConfig = {
  branches: [
    { name: 'develop', environments: ['dev'], agentAccess: 'full' },
    { name: 'pre-release', environments: ['test'], agentAccess: 'none' },
    { name: 'release', environments: ['uat', 'prod'], agentAccess: 'none' },
  ],
  featurePrefix: 'feature/*',
  defaultTarget: 'develop', // where feature branches PR into
  protected: ['pre-release', 'release'],
  agentAllowed: ['feature/*', 'develop'],
};
```

#### Config persistence

The `branchConfig` (along with other onboarding choices) is persisted to `agent_docs/.overlay-config.json` during onboard. This file is:
- Read by `regenerate.mjs` on subsequent runs so it can pass config to adapters without re-prompting
- Read by adapters that need branch config for dynamic content generation
- Committed to the repo so all team members share the same config

```js
// agent_docs/.overlay-config.json
{
  "version": 1,
  "branchConfig": { /* as above */ },
  "detectedStacks": ["react-typescript"],
  "selectedAgents": ["copilot", "claude", "codex"],
  "ciProvider": "azure-devops",
  "superpowersInstalled": true
}
```

#### Updated function signatures

All adapter `generate*` functions change from:
```js
generate(targetDir, coreDir, agentDocsDir, detectedStacks)
```
to:
```js
generate(targetDir, coreDir, agentDocsDir, overlayConfig)
// where overlayConfig = { detectedStacks, branchConfig, ciProvider, superpowersInstalled }
```

`regenerate.mjs` loads config via:
```js
const overlayConfig = JSON.parse(fs.readFileSync(path.join(agentDocsDir, '.overlay-config.json'), 'utf8'));
```

#### In agent_docs/branching_workflow.md

Replace the current hardcoded template with a dynamically populated version using `branchConfig`. The template will include:
- Branch names and their environment mappings
- The flow direction (feature → develop → pre-release → release)
- Which branches agents can interact with
- PR and merge rules per branch

#### In the analysis prompt

Add branch config context so the AI analysis step can refine the branching doc further based on what it observes in the repo (existing branches, CI triggers, merge policies).

### 2. CI/CD Pipeline Interaction with Branch Protection

#### Instruction-based guardrails (all adapters)

All generated instruction files will include explicit statements:

```markdown
## Branch Access Rules
You MAY push to and create PRs for: feature/*, develop
You must NEVER push to, merge into, or interact with: pre-release, release

These rules are non-negotiable. If asked to push to a protected branch, refuse and explain why.
```

#### Technical enforcement (Claude adapter)

`settings.json` deny rules generated dynamically from `branchConfig.protected` using Claude Code's permission pattern format:

```json
{
  "permissions": {
    "deny": [
      "Bash(git push*pre-release*)",
      "Bash(git push*release*)",
      "Bash(git merge*pre-release*)",
      "Bash(git merge*release*)",
      "Bash(git checkout -b pre-release*)",
      "Bash(git checkout -b release*)"
    ]
  }
}
```

These are appended to the existing deny rules already generated by the Claude adapter (e.g., `Bash(git push --force:*)`).

#### Technical enforcement (AGENTS.md / Codex)

OpenAI Codex respects `AGENTS.md` instructions but has no equivalent to Claude's `settings.json` deny rules. Branch protection for ChatGPT/Codex will be instruction-based only, with stronger reinforcement language given ChatGPT's tendency to need more explicit guardrails.

### 3. Superpowers Integration

#### During onboard.mjs

After agent selection, add a superpowers step:

```
Superpowers Plugin
──────────────────
The superpowers plugin provides a structured 4-phase AI workflow:
  Brainstorm → Plan → Execute → Complete

Install superpowers for Claude Code? [Y/n]
```

- Default: Yes
- If not installed: print manual install instructions for the user to run in Claude Code (`/install-plugin superpowers` or the current CLI mechanism). The onboard script cannot invoke Claude Code commands directly from Node, so this is a guided step rather than automatic execution.
- If already installed (detect via `~/.claude/plugins/` directory): skip with a note
- If user declines: skip, note in README-AGENTIC.md that it's recommended
- Fallback: The 4-phase workflow is encoded in all instruction files regardless of whether superpowers is installed. Superpowers enhances the workflow with structured skills but is not required for the workflow patterns to function.

#### In generated instruction files

All adapters reference the 4-phase workflow pattern:
1. **Brainstorm** — explore requirements, propose approaches, get approval before coding
2. **Plan** — break into small tasks with clear acceptance criteria
3. **Execute** — implement task-by-task with tests and commits
4. **Complete** — verify, review, merge/PR

This is encoded in the universal workflow section of each instruction file, not as a superpowers dependency — so it works even without the plugin installed.

### 4. Copilot Tiered Instruction Structure

#### File structure

```
.github/
├── copilot-instructions.md                # Universal workflow (all models)
├── instructions/
│   ├── claude.instructions.md             # Claude-specific patterns
│   ├── chatgpt.instructions.md            # ChatGPT-specific patterns
│   ├── branching.instructions.md          # Branch workflow & protection
│   └── ci-pipeline.instructions.md        # CI/CD interaction rules
```

#### Copilot adapter return contract

The Copilot adapter changes from returning a single file path to returning an array of generated file paths:

```js
// Old: return copilotInstructionsPath;
// New: return [copilotInstructionsPath, ...instructionFilePaths];
```

`onboard.mjs` and `regenerate.mjs` updated to handle array returns from all adapters (standardize all adapters to return arrays for consistency).

#### copilot-instructions.md (universal)

The primary instruction file. Contains:
- Core workflow principles (Observe First, Prescribe Never)
- 4-phase workflow (Brainstorm → Plan → Execute → Complete)
- Agent docs reference (what's in agent_docs/ and how to use it)
- Documentation requirements (research docs, ADRs, plans)
- Implementation guards (blast radius, proactive checkpoints)
- Git conventions (commit format, PR process)
- Branch access rules summary

Kept comprehensive but concise — this is always loaded into context.

#### claude.instructions.md

```yaml
---
applyTo: "**"
---
```

Claude-specific patterns:
- Leverage Claude's strong instruction-following — reference agent_docs by path
- Tool use patterns (Read before Edit, Grep over grep, etc.)
- Concise communication style
- Superpowers skill invocation (if installed)
- Memory system integration
- Model routing (when to use Opus vs Sonnet vs Haiku)

#### chatgpt.instructions.md

```yaml
---
applyTo: "**"
---
```

ChatGPT-specific patterns:
- More explicit workflow reinforcement — restate key rules with emphasis
- Step-by-step process reminders (ChatGPT benefits from procedural clarity)
- Stronger guardrail language for branch protection
- Explicit "do not" lists for common ChatGPT drift patterns
- Same workflow, more verbose encoding

#### branching.instructions.md

```yaml
---
applyTo: "**"
description: "Branch workflow and protection rules"
---
```

Populated from `branchConfig`:
- Full branch topology with environment mappings
- Flow direction diagram
- Agent access rules (allowed/denied)
- PR and merge conventions per branch
- Hotfix process

Note: Uses `applyTo: "**"` because branching rules apply regardless of which files are being edited. The content is kept concise (branch table + rules) to minimize context cost.

#### ci-pipeline.instructions.md

```yaml
---
applyTo: "**/.github/**,**/azure-pipelines*,**/Jenkinsfile,**/.gitlab-ci*,**/Dockerfile,**/docker-compose*"
description: "CI/CD pipeline interaction rules"
---
```

Uses targeted `applyTo` pattern — only loaded when editing CI/CD-related files, keeping context lean for normal development work.

- Detected pipeline type (GitHub Actions / Azure DevOps)
- What the agent can do (write commits, push to allowed branches, create PRs)
- What the agent cannot do (deploy, modify pipeline config, push to protected branches)
- How to check pipeline status
- Commit message format that triggers/skips CI

### 5. AGENTS.md Adapter (OpenAI Codex)

New adapter at `adapters/codex/generate.mjs`:

Generates `AGENTS.md` at project root with:
- Same workflow patterns as CLAUDE.md
- Written at higher verbosity for ChatGPT's instruction-following characteristics
- Explicit step-by-step processes
- Stronger guardrail reinforcement
- Branch protection rules (instruction-based, no technical enforcement available)
- Agent docs reference
- 4-phase workflow

### 6. README-AGENTIC.md

Generated in the target project root. Contains:

#### What This Provides
- Overview of the AI workflow overlay and its purpose
- What agent_docs are and how they guide AI assistants

#### The 4-Phase Workflow
- Brainstorm → Plan → Execute → Complete
- Brief description of each phase and why it matters

#### Instruction Files Explained
| File | Tool/Platform | Purpose |
|------|--------------|---------|
| `.github/copilot-instructions.md` | GitHub Copilot (VS Code) | Universal workflow rules applied to all Copilot interactions, regardless of which AI model is selected (Claude, ChatGPT, etc.) |
| `.github/instructions/claude.instructions.md` | GitHub Copilot with Claude | Claude-specific patterns and optimizations for when Claude is the selected model in Copilot |
| `.github/instructions/chatgpt.instructions.md` | GitHub Copilot with ChatGPT | ChatGPT-specific patterns and reinforcements for when ChatGPT is the selected model in Copilot |
| `.github/instructions/branching.instructions.md` | GitHub Copilot (all models) | Branch workflow, environment mappings, and agent access rules |
| `.github/instructions/ci-pipeline.instructions.md` | GitHub Copilot (all models) | CI/CD pipeline interaction rules and constraints |
| `CLAUDE.md` | Claude Code (CLI) | Project instructions for Claude Code's standalone terminal agent |
| `AGENTS.md` | OpenAI Codex (CLI) | Project instructions for OpenAI's Codex terminal agent |
| `.cursorrules` | Cursor IDE | Project instructions for Cursor's AI assistant |

#### Documentation Locations
| Directory | Purpose |
|-----------|---------|
| `agent_docs/` | AI-readable project documentation — architecture, conventions, workflows |
| `docs/research/` | Research documents created during the Brainstorm phase |
| `docs/plans/` | Implementation plans created during the Plan phase |
| `docs/decisions/` | Architecture Decision Records (ADRs) |
| `docs/superpowers/specs/` | Design specs from superpowers brainstorming sessions |
| `docs/superpowers/plans/` | Implementation plans from superpowers planning sessions |

#### Installing Superpowers
- What superpowers is and why it's recommended
- Installation command for Claude Code
- Note that it enhances the 4-phase workflow with structured skills

#### Keeping Docs Updated
- How to regenerate instruction files after agent_docs changes (`node scripts/regenerate.mjs`)
- When to update agent_docs (new patterns discovered, architecture changes, etc.)

#### Branch & CI Conventions
- Summary of the project's branching strategy
- Which branches agents can access
- Pipeline interaction rules

## Changes Required

### New Files
- `adapters/codex/generate.mjs` — AGENTS.md generator
- `adapters/codex/README.md` — adapter documentation
- `adapters/shared/build-readme-agentic.mjs` — README-AGENTIC.md generator (shared, called from onboard.mjs)
- `adapters/shared/build-branching-content.mjs` — dynamic branching content builder (shared, used by all adapters)
- `.github/instructions/` templates for `claude.instructions.md`, `chatgpt.instructions.md`, `branching.instructions.md`, `ci-pipeline.instructions.md`

### Modified Files
- `scripts/onboard.mjs` — add branching prompts, superpowers guided install step, Codex adapter call, tiered Copilot generation, write `.overlay-config.json`, generate README-AGENTIC.md
- `adapters/copilot/generate.mjs` — generate tiered instruction structure (5 files), return array of paths
- `adapters/claude/generate.mjs` — accept `overlayConfig` (new signature), dynamic deny rules from branchConfig, superpowers awareness
- `adapters/cursor/generate.mjs` — accept `overlayConfig` (new signature), add branch protection instructions
- `adapters/shared/build-slim-content.mjs` — accept `overlayConfig` (replaces `detectedStacks`), replace hardcoded Git Conventions section with dynamic summary from branchConfig pointing to `branching.instructions.md` / `agent_docs/branching_workflow.md`
- `core/agent_docs/branching_workflow.md` — replace hardcoded `main/develop/feature/*` template with parameterized template that uses `<!-- ONBOARDING: ... -->` comments referencing branchConfig fields
- `scripts/regenerate.mjs` — load `.overlay-config.json`, pass `overlayConfig` to all adapters, handle array return values, support tiered Copilot files
- `core/workflow.md` — update git conventions to reference configurable branching rather than prescriptive flow

### Existing Files (No Changes)
- Stack detection (`stacks/`) — unchanged
- CI templates (`scripts/ci-templates/`) — unchanged
- Doc skeleton generation — unchanged (but README-AGENTIC.md added to output)

### Backward Compatibility

Projects already onboarded with the current tool:
- `regenerate.mjs` checks for `.overlay-config.json`. If not found, falls back to current behavior (detect stacks, use hardcoded branching) and prints a warning suggesting re-running `onboard.mjs` for full configuration.
- Existing single-file `copilot-instructions.md` is preserved if tiered structure is not configured.

## Resolved Questions

1. **Config persistence** — stored in `agent_docs/.overlay-config.json`, loaded by `regenerate.mjs`
2. **Adapter signatures** — all adapters move to `(targetDir, coreDir, agentDocsDir, overlayConfig)` with `overlayConfig` containing `detectedStacks`, `branchConfig`, `ciProvider`, `superpowersInstalled`
3. **Adapter return values** — all adapters standardized to return arrays of generated file paths
4. **Superpowers install** — guided manual step (print instructions) since Node can't invoke Claude Code CLI; 4-phase workflow encoded in instructions regardless
5. **Claude deny rule format** — uses `Bash(command*)` pattern matching Claude Code's permission system
6. **Hardcoded branching in build-slim-content.mjs** — replaced with dynamic summary from branchConfig
7. **Codex adapter dispatch** — added as opt-in agent selection alongside Claude and Cursor (Copilot always generated)
8. **Context bloat** — `ci-pipeline.instructions.md` uses targeted `applyTo`; branching stays global but concise
9. **Environment field** — uses arrays (`['uat', 'prod']`) not comma-separated strings
